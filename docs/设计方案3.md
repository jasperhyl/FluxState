## 1\. 目标平台与编译路线

  * **目标平台**: `x86_64-unknown-linux-gnu`
  * **ABI 标准**: System V AMD64 ABI
  * **调用约定**: 公开运行时接口统一使用 C 调用约定 (`ccc`)。
  * **编译路线**: FluxState source -\> AST -\> Semantic Analysis -\> LLVM IR -\> Object File (`.o`) -\> Linker -\> Executable

 >**注**：开发与调试阶段可输出 `.s` 文本汇编，正式构建流水线直接输出原生目标文件 `.o`。

---

## 2\. 总体设计原则

FluxState 作为**面向状态机与事件驱动系统**的 DSL，其 Data Layout 优先服务于运行时热点（状态判断、事件分发、定时器检查）：

  * **公开 ABI 极简，内部布局自由**：仅对外部暴露指针、int、bool 和标量枚举，引擎内部布局由编译器全权掌控。
  * **编译期与运行时严格分离**：AST、状态图元数据、静态分析结构不进入运行时热路径。
  * **热路径标量化，实体对象紧凑化**：高频访问的 state、tag 使用标量；machine、event 采用紧凑内存布局；transition 直接 Lowering 为原生控制流，不作解释执行。

## 3\. 核心运行时实体 (Macro Level)

运行时以 Machine 为核心，统一管理环境、队列与定时器。

### 3.1 状态机与变量环境 (Machine & Environment)

变量环境坚决不使用通用的动态哈希表（如 `map<string, Value>`），而是由编译器为每个特定的状态机生成专属的静态结构体，以实现零哈希开销、零装箱/拆箱，并利于 LLVM GEP 优化。

```c
// 1. 状态机通用头部
typedef struct {
    uint32_t current_state;//当前状态
    uint32_t flags;//运行时标志位
    uint64_t entered_at_ns;//当前machine进入当前state的时间点
    struct FS_EventQueue* queue;//这个machine的事件队列
    struct FS_TimerTable* timers;//记录这个 machine 当前挂着哪些“未来要触发的时间事件”。当状态机进入某个带 after 的状态时，runtime 可以注册一个 timer
} FS_MachineHeader;

// 2. 编译器生成的专属变量环境
typedef struct {
    uint8_t busy;
    int32_t deny_count;
} FS_ENV_AccessControl;

// 3. 最终实例化的 Machine 结构
typedef struct {
    FS_MachineHeader hdr;
    FS_ENV_AccessControl env;
} FS_AccessControl_Machine;
```

> **注**：对于极简的 Machine，编译器可选择将 `FS_ENV_` 字段直接内联压平到 Machine 结构中。

### 3.2 事件队列 (Event Queue)

采用环形数组实现，结构简单、缓存友好，适合高频出入队。

```c
typedef struct FS_EventQueue {
    uint32_t head;
    uint32_t tail;
    uint32_t cap;
    struct FS_EV_Event* data;
} FS_EventQueue;
```

### 3.3 定时器表 (Timer Table)

初期采用紧凑数组表，满足绝大多数单机场景。

```c
typedef struct FS_TimerTable {
    uint32_t count;
    uint32_t cap;
    struct FS_Timer* data;
} FS_TimerTable;
```

## 4\. 领域与基础类型 (Micro Level)

### 4.1 事件 (Event)

所有事件由 Runtime 统一接管。一旦执行 `emit(e)`，事件即入队，调用方不得再修改或释放。Dispatch 完成后，由 Runtime 根据 `flags` 决定是否释放 payload。
```c
typedef struct {
 uint32_t tag;//标记事件，比如EV_CardScanned，EV_AuthOk
 uint32_t flags;//说明这个payload该不该由runtime释放
 uint16_t reserved;//这是个保留字段，后面可能会用于事件优先级，事件来源或者分发策略
 uint32_t payload_size;
 void* payload;//event附带的参数
 uint64_t timestamp_ns;//还没有确定这个字段是用于事件被创建，投递还是入队时间。应该是用于事件的创建时间
} FS_Event;
```

### 4.2 定时器 (Timer)

将 `after Xs -> S` 统一建模为事件驱动：进入状态时启动 Timer，超时后向自身队列投递一个内部事件（`FS_EV_TIMEOUT_...`），由统一的 Dispatch 循环处理。

```c
typedef struct FS_Timer {
    uint64_t deadline_ns;
    uint32_t event_tag;     // 超时后投递的内部事件 Tag
    uint16_t retry_left;
    uint8_t active;
    uint8_t kind;           // 一次性 / 周期性 / Retry
} FS_Timer;
```

### 4.3 状态与基础标量

  * **state**: 本质为枚举标签，定义为 `typedef uint32_t FS_State;`，便于 `switch` 分发。
  * **int**: 映射为 `i32`（满足绝大多数计数、索引、编号需求）。
  * **double**: 映射为 LLVM 原生 `double`。
  * **bool**: LLVM IR 中为 `i1`（利于分支优化），内存布局中为 `i8`（利于字节对齐）。
  * **string**: 采用“指针 + 长度”的胖指针表示，避免 C 风格 `\0` 结尾的缺陷。

<!-- end list -->

```c
typedef struct {
    char* data;
    uint64_t len;
} FS_String;
```

  * **set / map**: 作为 Opaque Pointer (`FS_Set*`, `FS_Map*`) 存在，具体内存操作（哈希、扩容）交由运行时 Helper 函数处理，简化编译器第一版的实现负担。

## 5. 状态迁移与行为逻辑 (Transition, Guard, Action)

`transition` 是语言的核心语义单位，但在主执行路径中**不建议作为解释器风格的大对象来驱动运行**。

### 5.1 Transition

* **执行时**：直接 lowering 为 `switch(current_state)` + `switch(event.tag)` + `if (guard)` 控制流。
* **分析时**：保留只读 metadata，仅供分析器和调试器（如 `visualize`、`check_unreachable`、`check_deadlock`）使用，不作为热路径执行的主要驱动形式。

```c
typedef struct {
    uint32_t src_state;
    uint32_t trigger_kind;   // event / timeout
    uint32_t trigger_id;     // event tag or timer id
    uint32_t dst_state;
    uint64_t timeout_ns;
    void* guard_fn;
    void* action_fn;
} FS_TransitionMeta;
```

### 5.2 Guard

`guard` lowering 为普通辅助函数：

```c
bool FS_Guard_3(FS_SmartCrossing_Machine* m, const FS_EV_Event* e);
```

### 5.3 Action

`action` lowering 为普通辅助函数：

```c
void FS_Action_5(FS_SmartCrossing_Machine* m, const FS_EV_Event* e);
```

## 6. 最终 Lowering 规则

FluxState 的语法构件最终按照下列方式 lowering：

* `state` -> `i32` tag
* `event` -> `FS_EV_Event`
* `machine` -> `FS_MachineHeader` + machine-specific env
* `from S on E -> T` -> `switch(current_state)` + `switch(event.tag)`
* `when cond` -> 条件分支 (调用辅助函数)
* `do { ... }` -> 普通基本块 / helper function
* `after 5s` -> timer record + 内部 timeout event
* `emit(e)` -> 向 event queue 入队 (不直接修改 current_state，由 runtime 按 FIFO 分发)
* `start_timer / cancel_timer` -> runtime helper
* `set / map` -> opaque pointer + runtime helper

## 7. 函数的运行时逻辑

FluxState 的运行时核心是一个高效的事件驱动循环，所有状态机实例都遵循统一的执行模型。入口函数为 `runtime()`，它负责驱动状态机从一个稳定状态转换到另一个稳定状态。

```c
void runtime(FS_MachineHeader* machine);
```

### 7.1 核心循环

`runtime()` 函数的逻辑遵循“拉取事件 -> 处理事件 -> 处理定时器 -> 循环”的模式，确保状态机对外部事件和内部超时做出及时响应。

```c
void runtime(FS_MachineHeader* machine) {
    // 1. 初始化: 执行初始状态
    //    对于新创建的machine，这相当于触发一次没有事件的特殊“进入”动作。
    current_state = machine->current_state;
    run_state_entry_actions(machine, current_state);

    // 2. 主循环: 持续运行直到状态机终止或显式停止
    while (machine->flags & FS_RUNNING) {
        // 2.1 从事件队列中拉取一个事件
        FS_Event* event = dequeue_event(machine->queue);
        if (event) {
            // 有事件到达，分发并处理
            dispatch_event(machine, event);
            // 事件处理后，由runtime根据event->flags决定是否释放payload
            if (event->flags & FS_EVENT_FREE_PAYLOAD) {
                free(event->payload);
            }
            // 事件结构体本身可以由环形队列管理或直接释放
            continue; // 处理完一个事件后，立即回到循环开始，处理下一个事件或定时器
        }

        // 2.2 没有事件时，检查定时器
        FS_Timer* expired_timer = check_timers(machine->timers);
        if (expired_timer) {
            // 有定时器超时，将其转换为内部超时事件并投递
            FS_Event timeout_event = {
                .tag = expired_timer->event_tag,
                .flags = 0, // 内部超时事件的payload由runtime管理，无需外部释放
                .payload = NULL,
                .payload_size = 0,
                // 时间戳可以设置为当前时间或超时时间
                .timestamp_ns = get_current_time_ns(),
            };
            // 将超时事件入队，并在下一次循环中立即处理
            enqueue_event(machine->queue, &timeout_event);
            // 更新定时器状态（例如，若为一次性定时器，则将其标记为非活跃）
            deactivate_timer(machine->timers, expired_timer);
            continue;
        }

        // 2.3 既无事件也无定时器超时，则进入休眠等待，避免CPU空转
        //    这是一个优化点，可以通过 futex 或 eventfd 等机制实现。
        wait_for_events_or_timeout(machine);
    }

    // 3. 退出循环: 执行状态机清理工作（如释放所有定时器、清空队列等）
    cleanup_machine(machine);
}
```

### 7.2 状态进入与退出

在 `dispatch_event()` 函数中，状态迁移的逻辑被精确实现：

1.  **调用当前状态的退出动作**：在状态切换前，执行 `on_exit` 中定义的代码。
2.  **执行迁移**：根据当前状态和事件，查找并执行匹配的迁移（`transition`）。迁移中可能包含 `guard` 和 `action`。
3.  **更新状态**：将 `machine->current_state` 更新为目标状态。
4.  **调用新状态的进入动作**：执行 `on_entry` 中定义的代码。

```c
static void dispatch_event(FS_MachineHeader* machine, const FS_Event* event) {
    FS_State current = machine->current_state;
    FS_State next = current;

    // 1. 根据状态和事件，查找并执行迁移
    //    这里的查找逻辑在编译时已被lowering为 switch 或 lookup table，性能极高。
    bool transition_found = find_and_execute_transition(machine, current, event, &next);

    if (transition_found) {
        // 2. 执行状态切换的完整生命周期
        //    a. 执行当前状态的退出动作
        call_state_exit_actions(machine, current);
        //    b. 执行状态迁移中的动作（如果尚未在find_and_execute_transition中执行）
        //    c. 更新状态
        machine->current_state = next;
        //    d. 更新时间戳
        machine->entered_at_ns = get_current_time_ns();
        //    e. 执行新状态的进入动作
        call_state_entry_actions(machine, next);
    } else {
        // 3. 未找到迁移的处理
        //    根据配置，可以忽略事件、记录错误或触发异常。
        handle_unhandled_event(machine, event);
    }
}
```

### 7.3 定时器触发逻辑

`check_timers()` 函数遍历 `FS_TimerTable`，找到所有 `deadline_ns <= current_time_ns` 且处于 `active` 状态的定时器。它返回最早超时的定时器，以确保超时事件的投递顺序与超时时间一致。

*   **一次性定时器**：超时后，其 `active` 标志被置为 0，后续不再触发。
*   **周期性定时器**：超时并投递事件后，其 `deadline_ns` 被更新为 `current_time_ns + period_ns`，`active` 标志保持为 1。
*   **重试（Retry）定时器**：超时后，如果 `retry_left > 0`，则 `retry_left` 减 1，并重新设置 `deadline_ns`，等待下一次触发。

### 7.4 执行模型

*   **单线程 / 协程友好**：`runtime()` 函数本身不是线程安全的。对于多实例并发，推荐每个状态机实例运行在独立的线程或协程中，或由上层调度器保证对同一实例 `runtime()` 调用的串行化。这种设计避免了锁竞争，提升了热路径性能。
*   **无栈 / 有栈平衡**：由于 `guard`、`action` 和 `on_entry/exit` 被 lowering 为普通 C 函数，`runtime()` 的调用栈非常浅，适合在协程或用户态线程环境中运行。
