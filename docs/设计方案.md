## 1. 目标平台、ABI 与编译路线

本语言的实现目标平台选择为 **`x86_64-unknown-linux-gnu`**，并遵循 **System V AMD64 ABI**。在 LLVM 中，目标平台由 **target triple** 指定，格式为 `<arch><sub>-<vendor>-<sys>-<abi>`；LLVM 官方教程也推荐通过 `TargetMachine` 创建目标信息，并将 `setTargetTriple(...)` 与 `setDataLayout(TargetMachine->createDataLayout())` 写回模块，以保证生成代码的布局和调用约定与目标平台一致。System V AMD64 ABI 的最新版维护入口可使用 x86-64 psABI 的官方 GitLab 项目页。([LLVM][1])

本项目采用的编译路线是：

`FluxState source -> AST -> semantic analysis -> LLVM IR -> object file (.o) -> linker -> executable`

也就是说，**不要求先手写文本汇编再交给外部汇编器**。LLVM 既可以输出文本汇编，也可以直接输出原生目标文件；`llc` 官方文档明确支持 `-filetype=asm` 和 `-filetype=obj` 两种输出形式。因此，本项目推荐**开发时可输出 `.s` 观察代码生成结果，正式流水线直接输出 `.o`**。([LLVM][2])

公开运行时接口统一使用 **C calling convention (`ccc`)**。LLVM LangRef 明确说明：如果没有显式指定，调用默认使用 C 调用约定；而且动态 caller/callee 的 calling convention 必须匹配，否则行为未定义。对于仅在编译器内部使用的辅助函数，LLVM 也提供 `fastcc` 等更偏内部优化的调用约定，但第一版实现不需要引入这些额外复杂度。([LLVM][3])

## 2. 总体设计原则

FluxState 是一个面向**状态机与事件驱动系统**的 DSL，因此 data layout 的设计目标不是“尽量像通用 OO 语言”，而是优先服务以下运行时热点：

1. 当前状态判断
2. 事件分发
3. 定时器超时检查

因此，本语言采用以下三条设计原则：

### 2.1 公开 ABI 简单，内部布局自由

ABI 只强约束**公开接口**，因此对外部运行时 API 只暴露简单类型，例如：

* 指针
* `int`
* `bool`
* 简单枚举 tag

而 DSL 内部的对象布局，例如 `machine`、`event`、`timer`、`environment`，由编译器自行设计。

### 2.2 编译期对象与运行时对象分离

下列内容属于**编译期对象**，不进入热路径运行时布局：

* AST
* 源代码级 transition 文本
* `visualize(machine)` 使用的图结构
* `check_unreachable` / `check_deadlock` 的分析图

真正需要进入运行时布局的，只包括：

* 当前状态
* 变量环境
* 活跃定时器
* 待处理事件队列

### 2.3 热路径尽量标量化，实体对象紧凑化

* `state`、`event tag`、`flag`、计数器等尽量用标量
* `machine`、`event`、`timer` 这种天然多字段实体用紧凑记录表示
* `transition` 不解释执行，直接 lowering 成控制流

这样既保留清晰的语义结构，也有利于 LLVM 优化。

## 3. 最终 data layout 方案


### 3.1 基础类型

#### `int`

表示为 `i32`。

理由：
状态机 DSL 中，大多数整数只用于计数、索引、状态编号、事件编号、重试次数等，`i32` 已经足够，且比默认使用 `i32` 更紧凑。

#### `double`

表示为 LLVM `double`。

#### `bool`

* IR 中使用 `i1`
* 内存中使用 `i8`

理由：
`i1` 适合条件判断和分支；`i8` 更适合作为结构体字段存储，布局更直接。

#### `string`

表示为“指针 + 长度”：

```c
typedef struct {
    char* data;
    uint64_t len;
} FS_String;
```

理由：
这种表示比 C 风格 `char*` 更稳定，不依赖空字符结尾，也便于比较、切片和日志输出。

---

### 3.2 领域类型

#### `state`

表示为 `i32` 枚举标签：

```c
typedef uint32_t FS_State;
```

理由：
状态本质上是一个枚举值，而不是复杂对象。`i32` 易于 `switch` 分发，也便于调试和扩展。

---

#### `event`

建议采用**紧凑固定头部**，而不是通用 heap payload 指针。推荐如下：

```c
typedef struct {
    uint32_t tag;
    uint32_t arg0;
    uint32_t arg1;
    uint64_t timestamp_ns;
} FS_Event;
```

理由：

1. 这是第一版设计方案，先尽量简单
2. 固定头部避免了为每个事件额外分配 payload 对象。
3. 事件队列可以直接存放连续的 `FS_Event` 数组，缓存局部性更好。
4. 比 “`tag + payload pointer`” 更容易实现，也更容易优化。

如果以后事件参数需要扩展，再升级为 `tag + payload pointer` 也很自然；但第一版推荐先用紧凑表示。

---

#### `timer`

建议表示为独立记录：

```c
typedef struct {
    uint64_t deadline_ns;
    uint32_t event_tag;
    uint16_t retry_left;
    uint8_t active;
    uint8_t kind;
} FS_Timer;
```

其中：

* `deadline_ns`：超时时刻
* `event_tag`：超时后自动投递的内部事件
* `retry_left`：剩余重试次数
* `active`：是否处于激活状态
* `kind`：一次性 / 周期性 / retry timer

理由：
`after 10s -> S` 在运行时不直接实现为“时间一到就跳转”，而是统一建模为：

> 进入状态时启动 timer；timer 到期后向事件队列投递一个内部事件；dispatch 再处理该事件。

这样整个语言都保持“事件驱动”这一条主线，语义最统一。

---

#### `machine`

`machine` 是运行时的核心对象。推荐使用：

```c
typedef struct {
    uint32_t current_state;
    uint32_t flags;
    uint64_t entered_at_ns;
    struct FS_EventQueue* queue;
    struct FS_TimerTable* timers;
} FS_MachineHeader;
```

对于具体 machine，再附加专门的环境结构：

```c
typedef struct {
    uint8_t ped_waiting;
} SmartCrossing_Env;

typedef struct {
    FS_MachineHeader hdr;
    SmartCrossing_Env env;
} SmartCrossing_Machine;
```

理由：

1. `current_state` 是最热字段，必须直接放在 machine 中。
2. `entered_at_ns` 用于 timeout 判定。
3. 队列和 timer 表都归属于 machine，符合语言语义。
4. 环境字段由编译器为每个 machine 单独生成，避免运行时用哈希表查变量。

如果某个 machine 很简单，也可以进一步压平，直接把环境字段内联到 machine 中，而不单独保留 `Env struct`。

---

### 3.3 变量环境（environment）

这是整个方案里最关键的一点：

**变量环境不要实现成通用 `map<string, Value>`。**

而应当为每个 machine 生成专用环境结构。例如：

```c
typedef struct {
    uint8_t ped_waiting;
    int32_t retry_count;
} SomeMachine_Env;
```

理由：

* 避免哈希查找
* 避免装箱/拆箱
* 类型明确
* LLVM 更容易做 GEP 和优化
* 访问速度远高于通用动态 environment

也就是说：

* 语言语义上存在 “variable environment”
* 机器实现上应将其编译为**静态字段布局**

---

### 3.4 `set` / `map`

如果语言保留 `set` 和 `map` 类型，第一版实现建议将其表示为**opaque runtime handle**：

```c
typedef struct FS_Set FS_Set;
typedef struct FS_Map FS_Map;
```

在 IR 和运行时中将其当作指针处理：

```c
FS_Set*
FS_Map*
```

理由：
第一版无需把哈希表布局、扩容、迭代器等复杂机制全部塞进编译器；相关操作通过 runtime helper 函数处理即可。

## 4. transition、guard、action 的表示

### 4.1 transition

`transition` 是语言的核心语义单位，但**不建议在主执行路径中把 transition 作为解释器风格的大对象来驱动运行**。

第一版推荐：

* **执行时**：直接 lowering 为 `switch(current_state)` + `switch(event.tag)` + `if (guard)`
* **分析时**：保留只读 metadata，用于 `visualize`、`check_unreachable`、`check_deadlock`

例如可选的元数据结构：

```c
typedef struct {
    uint32_t src_state;
    uint32_t trigger_kind;   // event / timeout
    uint32_t trigger_id;     // event tag or timer id
    uint32_t dst_state;
    uint64_t timeout_ns;
    void* guard_fn;
    void* action_fn;
} FS_TransitionMeta;
```

但这个结构主要给分析器和调试器使用，不作为热路径执行的主要驱动形式。

---

### 4.2 guard

`guard` lowering 为普通辅助函数：

```c
bool guard_3(SmartCrossing_Machine* m, const FS_Event* e);
```

理由：
guard 需要访问 machine 环境和事件参数，因此函数形式最自然。

---

### 4.3 action

`action` lowering 为普通辅助函数：

```c
void action_5(SmartCrossing_Machine* m, const FS_Event* e);
```

理由：
action 负责更新环境、发出日志、启动/取消 timer、投递事件等，本质上就是一段普通过程代码。

---

## 5. 队列与 timer 表

### 5.1 事件队列

推荐使用环形数组：

```c
typedef struct FS_EventQueue {
    uint32_t head;
    uint32_t tail;
    uint32_t cap;
    FS_Event* data;
} FS_EventQueue;
```

理由：

* 结构简单
* 入队/出队开销小
* 连续内存布局好
* 适合事件驱动系统

---

### 5.2 timer 表

第一版直接使用简单数组表即可：

```c
typedef struct FS_TimerTable {
    uint32_t count;
    uint32_t cap;
    FS_Timer* data;
} FS_TimerTable;
```

如果后续 timer 数量非常多，再考虑最小堆等更复杂的数据结构。

---

## 6. 最终 lowering 规则

FluxState 的语法构件最终按照下列方式 lowering：

* `state` -> `i32` tag
* `event` -> `FS_Event`
* `machine` -> `FS_MachineHeader + machine-specific env`
* `from S on E -> T` -> `switch(state)` + `switch(event.tag)`
* `when cond` -> 条件分支
* `do { ... }` -> 普通基本块 / helper function
* `after 5s` -> timer record + 内部 timeout event
* `emit(e)` -> 向 event queue 入队
* `start_timer / cancel_timer` -> runtime helper
* `set / map` -> opaque pointer + runtime helper

这套 lowering 的优点是：

1. 语言语义清晰
2. 执行路径简单
3. 便于 LLVM 优化
4. 容易解释 ABI 与机器表示之间的关系
